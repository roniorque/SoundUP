# PRD 0001: SoundUp — per-app volume control and boost

**Last updated:** Saturday, Aug 8, 2026, 4:00 PM (UTC+8)
**Engagement:** `soundup`
**Source idea:** [docs/ideas/0001-soundup/0001-idea.md](../../ideas/0001-soundup/0001-idea.md)

## Problem Statement

Mac users running multiple audio-producing apps at once (music, calls, browser tabs,
notifications) have no built-in, free way to control each app's volume independently. macOS only
offers one global system volume, shared by every app. Users also can't push a specific app louder
than its own maximum volume when that app's own ceiling is too quiet relative to others — the only
existing solution to either problem is Rogue Amoeba's SoundSource, a closed-source, ~$50 paid
utility.

## Solution

SoundUp is a free, open-source macOS menu-bar app. Clicking its icon shows a live list of apps
currently producing audio, each with its own volume slider (0–200%) and mute button. 100% is the
app's own normal maximum; values above 100% apply digital gain to make that app play louder than
it normally could, with soft limiting to control clipping. Adjustments only affect the selected
app — every other app, and the system volume, are untouched. Settings persist per app across
restarts and reboots. Distribution is entirely free: source and releases on GitHub, installable
via a Homebrew tap, unsigned, no Apple Developer account or fee involved.

## User Stories

1. As a Mac user with music and a video call running simultaneously, I want to lower the music
   app's volume independently, so that I can hear the call clearly without pausing the music.
2. As a Mac user, I want to mute a specific app (e.g. a notification sound from Slack), so that it
   doesn't interrupt what I'm currently listening to.
3. As a Mac user with an app whose audio is too quiet even at its own 100% volume, I want to boost
   that app above its normal maximum, so that I can actually hear it clearly.
4. As a user boosting an app's volume, I want the audio to remain reasonably listenable even when
   boosted, so that I don't just get harsh, unusable distortion.
5. As a user, I want to see, at a glance, only the apps that are currently playing audio, so that
   I don't have to hunt through every running app to find the one I want to adjust.
6. As a user, I want the app list to update automatically as apps start or stop playing audio, so
   that I don't have to manually refresh or reopen the menu.
7. As a user, I want my per-app volume/boost settings to be remembered the next time that same app
   plays audio, so that I don't have to redo the same adjustment every session.
8. As a user, I want my settings to survive quitting and relaunching an app, so that my preferred
   volume for that app is always applied automatically.
9. As a user, I want my settings to survive a full system reboot, so that my setup persists across
   days, not just within a single session.
10. As a user, I want the app to live only in the menu bar (no dock icon, no separate window), so
    that it feels like a lightweight system utility rather than a full application.
11. As a user, I want the app to work without installing a virtual audio driver or kernel
    extension, so that setup is simple and doesn't require a system restart or extra system
    extension approval flows beyond the audio-capture permission itself.
12. As a privacy-conscious user, I want to understand that the app needs a one-time system
    permission grant to read/adjust other apps' audio, so that I'm not surprised by an OS
    permission prompt.
13. As a user who doesn't want to pay for software, I want to install SoundUp entirely for free —
    no purchase, no subscription, no Apple Developer fee passed on to me — so that the tool
    remains genuinely free.
14. As a technically comfortable user, I want to install SoundUp from the terminal via Homebrew,
    so that I don't have to manually download a zip and drag it into Applications.
15. As a user without Homebrew, I want to be able to download a pre-built release directly from
    GitHub, so that Homebrew isn't a hard requirement to use the app.
16. As a user encountering the unsigned-app Gatekeeper/permission prompt for the first time, I
    want clear documentation on how to proceed, so that I'm not blocked or confused by macOS
    security warnings.
17. As an open-source contributor, I want the source code publicly available on GitHub, so that I
    can inspect, audit, or contribute to the project.
18. As a user, I want volume/boost adjustments to apply in real time as I move the slider, so that
    I can dial in the right level by ear.
19. As a user on macOS older than 14.4, I want the app (or its documentation) to clearly tell me
    it isn't supported on my system, so that I don't waste time trying to install something that
    can't work.
20. As a user, I do not expect SoundUp to let me route different apps to different physical output
    devices, since that is explicitly out of scope for this version.

## Implementation Decisions

- **Platform:** Native macOS app, Swift/SwiftUI, macOS 14.4 (Sonoma) or later only. No
  cross-platform support.
- **Audio capture/control mechanism:** Apple's Core Audio **Process Tap API**
  (`AudioHardwareCreateProcessTap` and related Audio Hardware Services calls) to tap and apply
  gain to a specific process's audio in real time. No virtual audio driver, no kernel extension,
  no system extension install flow — only the OS-level audio-capture permission prompt.
- **App shape:** Menu-bar (status item) only. No dock icon, no main window. All interaction
  happens through the status-item dropdown.
- **App list behavior:** The dropdown lists only apps currently producing audio. The list updates
  dynamically (apps appear when they start producing sound, disappear when they stop), driven by
  Core Audio process-audio-activity notifications rather than a fixed/static app list.
- **Volume control range:** Per-app slider from 0% (muted) to 200%. 100% represents the app's own
  unmodified/unity output level. Values 100–200% apply additional digital gain via the Process
  Tap, with a soft limiter engaged above 100% to reduce hard clipping.
- **Mute:** A dedicated mute control per app, independent of and overriding the slider value
  (slider position is preserved while muted, so unmuting restores the prior level rather than
  resetting to 100%).
- **Persistence:** Per-app volume/boost/mute settings are keyed by the app's **bundle identifier**
  and persisted to local disk (e.g. `UserDefaults` or a local JSON/plist store — exact storage
  mechanism is an implementation detail for Phase 5, not fixed here). On app launch and whenever a
  process starts producing audio, SoundUp checks for a stored setting keyed by that bundle ID and
  re-applies it automatically.
- **Scope boundary — no routing:** All apps continue to play through the current macOS default
  output device. SoundUp does not create virtual/aggregate devices and does not offer a
  per-app output-device selector in this version.
- **Permissions:** The app will trigger the macOS system permission prompt required for the
  Process Tap / audio-capture entitlement on first use. The app must handle the case where the
  user denies the permission (clear in-app messaging, no crash) and the case where the process tap
  is unavailable (macOS version below 14.4 — app should detect this and inform the user rather
  than fail silently).
- **Distribution:** No Mac App Store submission. Source and built releases published on a public
  GitHub repository. A companion Homebrew tap repository provides `brew install --cask` support.
  The app ships **unsigned** (no Apple Developer Program membership, no notarization) — Homebrew
  Cask's install process strips the quarantine attribute, avoiding the standard Gatekeeper
  "unidentified developer" block; a direct GitHub-zip download by a user not using Homebrew may
  still need a manual one-time Gatekeeper bypass, which must be documented in the repo README.
- **UI patterns:** No existing UI/design-system to match — this is a new, empty repository.
  SoundUp will follow standard native macOS menu-bar app conventions (SwiftUI `MenuBarExtra` or
  equivalent, system-standard sliders and buttons) rather than a custom visual design system.

## Testing Decisions

- Tests should verify **observable behavior**, not internal implementation: e.g. "setting a given
  app's slider to 150% results in that app's captured audio stream being scaled to roughly 1.5x
  amplitude with limiting engaged," not "the limiter function was called with argument X."
- **Persistence logic** (save/restore of per-app settings keyed by bundle ID) should be
  unit-testable independently of the live Core Audio Process Tap, since it's pure
  read/write-to-disk logic.
- **Gain/limiting math** (mapping slider percentage to applied gain, and the soft-limiter curve
  above 100%) should be unit-tested as a pure function, independent of any live audio hardware.
- **Process Tap integration** (actually creating a tap, receiving audio-activity notifications,
  applying gain to a live stream) is difficult to fully unit test since it depends on Core Audio
  and running processes; this should be covered primarily via manual/integration testing during
  Phase 5 build and Phase 9 QA, with any test doubles/protocols for the Core Audio boundary
  designed to keep the rest of the app's logic testable in isolation.
- No prior art exists in this repository (brand-new project) — testing conventions will be
  established from scratch during Phase 5, following standard Swift/XCTest practices.

## Out of Scope

- Per-app output device routing (sending different apps to different physical outputs).
- Per-app input/microphone routing or control.
- Per-app audio effects (EQ, compressor, etc.).
- Multi-output / simultaneous output to more than one device.
- Mac App Store distribution.
- Support for macOS versions earlier than 14.4.
- Windows/Linux support or any cross-platform variant.
- Code signing/notarization paid for via an Apple Developer Program membership.

## Further Notes

- The macOS-14.4+ requirement and the "no Apple Developer fee" constraint are the two hardest,
  least-flexible boundaries on this project — both were deliberately chosen during Phase 1
  grilling to keep the project achievable at $0 cost using only Apple's supported, documented
  APIs.
- Because the Process Tap API is relatively new, Phase 5 build work should validate early that
  the exact tap/gain-application approach works reliably across a range of common apps (browsers,
  Spotify, Zoom, etc.) before investing further in UI polish.
