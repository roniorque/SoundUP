# Idea 0001: SoundUp — per-app volume control and boost for macOS

**Last updated:** Saturday, Aug 8, 2026, 3:00 PM (UTC+8)
**Engagement:** `soundup`

## Problem

macOS has no built-in, free way to control the volume of individual apps independently, or to
push a specific app's volume louder than its own normal maximum. Rogue Amoeba's SoundSource
solves this (and more), but it is closed-source and paid (~$50). Users who just want independent
per-app volume — and the ability to boost a quiet app past its own ceiling — have no free,
open-source alternative.

## Target users

Mac users who run multiple audio-producing apps at once (e.g. music + calls + notifications) and
want independent control over each app's loudness, including apps whose native volume ceiling is
too quiet, without paying for a commercial utility or accepting closed-source software.

## Constraints

- **macOS 14.4 (Sonoma) or later only** — v1 depends on Apple's Core Audio Process Tap API
  (`AudioHardwareCreateProcessTap`), which does not exist on earlier macOS versions. No fallback
  to a virtual-driver/kext approach is in scope.
- **$0 budget** — no Apple Developer Program membership (no $99/yr), no Mac App Store
  distribution, no notarization. Distribution is via a public GitHub repo (source + releases)
  plus a self-hosted Homebrew tap for terminal installs (`brew install --cask`). The app ships
  unsigned; Homebrew Cask installation strips the quarantine flag, avoiding the Gatekeeper
  "unidentified developer" block on launch. The macOS permission prompt for the audio-capture
  entitlement may still show as unidentified on first grant — accepted as a one-time, minor
  speed bump rather than a blocker.
- **Native macOS app only** — no cross-platform (Windows/Linux) support; no browser-extension
  variant.
- **Free and open-source** — license to be chosen in a later phase, but must permit free
  redistribution and source access.

## Out of scope for v1

- Per-app **output device routing** (e.g. sending different apps to different physical outputs
  simultaneously). Explicitly deferred — v1 is volume/boost only, and every app continues to play
  through the current system default output device.
- Per-app **input** routing/control.
- Per-app **audio effects** (EQ, compressor, etc.).
- Mac App Store distribution.

## Feature scope (v1)

- Menu-bar (status bar) app only — no dock icon, no main window.
- Clicking the menu-bar icon shows a dropdown list of apps **currently producing audio**, updated
  dynamically as apps start/stop making sound. Apps not currently playing audio are not listed.
- Each listed app gets:
  - A volume slider ranging **0% (muted) to 200%**, where 100% = that app's own normal full
    volume (system + app volume both maxed), and values above 100% apply digital gain via the
    Process Tap API, with soft limiting applied above 100% to control clipping/distortion.
  - A mute button.
- Per-app volume/boost settings **persist to disk keyed by app bundle ID**, and are automatically
  restored whenever that app next produces audio (including after app relaunch or system reboot).

## Success criteria

v1 is done when a user can: open the menu bar, see the list of apps currently playing audio,
independently adjust any listed app's volume from 0–200% without affecting system volume or other
apps' volume, hear an audible loudness increase above 100% with acceptable (limited) distortion,
and have those settings persist across app restarts and reboots — all installable for free via
GitHub/Homebrew, with no App Store listing and no Apple Developer fee paid.

## Design foundations

Not applicable in the usual greenfield sense. SoundUp is a native macOS menu-bar utility with a
minimal, standard system UI (status-bar dropdown, sliders, mute buttons) — there is no web
frontend, and no custom visual-branding decision to make via a multi-direction mockup contest.
UI will follow standard macOS menu-bar app conventions (SwiftUI), deferred to Phase 5 (Build).

## Open questions

None outstanding — all major decisions (platform, scope, technical approach, boost mechanics, UI
shape, app-list behavior, persistence, distribution/cost, naming, success criteria) were resolved
during grilling.
